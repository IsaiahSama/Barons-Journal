# Baron's Journal UI: Design

Date: 2026-11-13
Status: approved 2026-11-13

## Intent

Baron's Journal is a companion for playing Barony. While playing, the user keeps wanting to write things down or look them up: what's on this floor, which scroll label was fire, how to brew a potion. Today that ends up scattered in an unorganised text file. The app replaces that with one full-screen window on a **second monitor**, beside the game, that shows the current run's state from the save file, holds notes for the run and each floor, and has the reference material at hand.

The non-UI layers (`data`, `data.ids`, `reference`, `journal`) are built and tested. This design covers the PySide6 UI on top of them. **`docs/data-layer.md` is the API reference and the source of the rules the UI must follow. Read it alongside this document.**

## Goals

- One full-screen window that shows the **current run** and follows Barony's latest save, refreshing on its own when the game writes a new one.
- Read-only run stats: character, HP/MP, attributes, skills, level/exp, gold, hunger, equipment, visible effects, backpack, learned spells, kills.
- A scratchpad note for the run and a note per floor, saved automatically.
- Reference: the floor map (secret levels, artifacts, orbs), the alchemy recipe table, and scroll-label identification.
- Two layouts (C, the default, and A), switchable from the menu.
- A menu option to **open a past run** (runs browser), and a menu option to **pick which save slot** to follow.

## Non-goals

- An overlay or always-on-top mini window. It's a normal window on another monitor.
- Free-floating or draggable panels (see Approaches).
- Anything the data layer lists under "Not built yet": hotbar, inventory grid positions, other multiplayer players, learned alchemy recipes, an inventory-aware mixing helper.
- Packaging or installers.

## Anti-goals (failure even if it "works")

- **Spoilers.** Showing what an unidentified item really is, anywhere: name, tooltip, sort order, grouping, debug text (data-layer rule 1). Working out scroll labels from the seed.
- **Losing typed notes**: on run switch, layout switch, save refresh, or quit.
- **Crashing or blanking** on a bad or mid-write save. The last good data stays on screen (rule 5).
- **Yanking the user** out of what they're reading or typing when a save changes.
- Writing to any game file (rule 7).

## Constraints

- PySide6 (Qt 6) Widgets. UI code lives in `src/barons_journal/ui/`. `data`, `reference` and `journal` must not import Qt. The only changes outside `ui/` are the secret-level ones described below.
- The UI only uses the typed objects from those packages. It never reads raw save JSON or queries SQLite directly.
- All `Journal` calls happen on the main thread (rule 6). Parsing takes milliseconds, so everything runs on the main thread and there are no worker threads.
- `journal.record_run(save)` runs on every successful load, before any other journal call for that run (rule 2).
- The stats always carry the snapshot caption: "As of floor N, saved HH:MM" (rule 3).
- Hidden effects are filtered out (rule 4).

## Approaches considered

1. **Splitters with panel swapping (chosen).** The panels are self-contained widgets. Layouts A and C are two `QSplitter` arrangements, and switching moves the *same panel instances* between them, so no state is lost. A controller `QObject` owns the save watching, the journal and the live/past state, and signals the panels.
2. **Dock widgets.** Free arranging and floating, but "three equal columns" fights `QMainWindow`'s mandatory central widget, `saveState`/`restoreState` is fragile, and floating windows add states. Rejected: the user wants two fixed layouts, not free-form arranging.
3. **Qt Quick/QML.** No benefit for a data-dense tool, and it splits the stack across two languages. Rejected.

The user picked 1. Floating a single panel could be added later without a redesign.

## Decided by the user

- A full-screen window on a second monitor.
- The window shows the current run only. Past runs open through a **Run → Switch run…** browser, and a **save slot picker** is in the menu.
- Layouts A and C, switchable from the menu, **default C**.
- When the live save changes to a different run while the user is viewing a past run, the app **stays put and shows a banner** ("New run detected: view live run") instead of switching.
- Built with the splitter approach.
- **Secret levels get their own notes**, separate from the main floor at the same depth (see "Secret levels").

## The design

### Window

```
┌ File  Run  View ──────────────────────────────────────────────────────────┐
│ Brom · Human Warrior · Lv 4 · Floor 3 (Mines)    As of floor 3, saved 14:02│  ← run header
│ [banner area: new run detected / save read error / viewing past run]      │
├────────────┬──────────────────────────────────────────┬──────────────────┤
│ Character  │ [Backpack] Floors  Alchemy  Scrolls Kills│ Floor 3 notes    │
│            │                                          │ Run notes        │
└────────────┴──────────────────────────────────────────┴──────────────────┘
Layout C (default): Character | centre tabs (wide) | Notes, sizes roughly 1 : 2.5 : 1.1
```

```
Layout A (Dashboard): three roughly equal columns
┌────────────────────┬────────────────────┬──────────────────────────────┐
│ Character          │ Floor N notes      │ [Floors] Alchemy  Scrolls    │
│  …                 │ Run notes          │                              │
│ Backpack + spells  │                    │                              │
│ Kills              │                    │                              │
└────────────────────┴────────────────────┴──────────────────────────────┘
```

In layout A, Backpack and Kills move out of the tab widget and stack under Character, in the left column (a vertical splitter or a scroll area). The right column's tabs are Floors, Alchemy and Scrolls. In layout C, all five are tabs in the centre. The panel *instances* are the same in both layouts; only where they sit changes.

### Menus

- **File:** Choose save folder… · Quit
- **Runs:** Switch run… (runs browser) · Save slot… (slot picker) · Back to live run (enabled only while viewing a past run)
- **View:** Layout ▸ (● Focus (C) / ○ Dashboard (A), exclusive) · Show Character panel · Show Notes panel (checkable; they hide or show those panels in either layout)

### Panels

**Runs header** (always shown): character name, race, class, level, floor number and area (`floor_at(dungeon_lvl).area`), and the snapshot caption. Below it is a banner area for, in priority order: a save read error ("Couldn't read the save: <message>. Showing the last good data."), "New run detected: [View live run]", and "Viewing a past run: [Back to live run]".

**Character:** HP and MP as bars with numbers, level/exp, gold, hunger, the six attributes, the 16 skills (`proficiencies_by_name`), the 10 equipment slots from `equipment.slots()` (shown as "—" when empty), and the visible effects with time remaining (`seconds_remaining`, shown as "∞" when it's `None`).

**Notes:** two plain-text editors:
- **Floor N notes:** follows the current floor of the run being viewed.
- **Run notes:** the run's scratchpad.

**Backpack:** items from `[i for i in inventory if not i.equipped and not i.is_spell]`, with `name`, `count` and `status_name`. Blessing or curse is shown only when `identified` is true. A separate "Spells" list shows the `is_spell` items. The order is inventory order, never sorted by type.

**Floors:** a table of the 36 floors: number, area, secret entrance (with "50%" for chance 0.5), the secret level it leads to, artifacts there, the mystic orb, and a "📝" marker if the floor has a note. The current floor is highlighted. Selecting a row shows a detail area: the secret level's `treasures` and an editor for that floor's note.

**Alchemy:** a grid with the 6 bases as rows and the 8 secondaries as columns, each cell from `mix(base, secondary)` (the result name, or "random", "explodes", "×2 <potion>", "same"). There's also a "How do I make…" combo box that lists `recipes_making(result)`. This is static reference knowledge, not inventory, so it shows every potion.

**Scrolls:** follows the data layer's "Suggested scroll screen": one row per label in `SCROLL_LABELS`. An identified row shows the scroll name and effect plus an Undo button (`forget_scroll`). An unknown row shows a picker filled from `candidates(label)`. Picking calls `identify_scroll`, then the tab re-reads `scroll_progress` and redraws. A `JournalError` is shown inline or in a message box and nothing changes. A side panel lists "Still to find" from `remaining`.

**Kills:** monster → count from `kills_by_monster`, sorted by count (highest first), with monster names capitalised.

### Live run vs past run

The app has two view modes, owned by the controller:

- **Live:** shows the followed save. All panels are filled from `SaveFile`. Notes and scroll identifications can be edited.
- **Past run** (opened from the runs browser): the journal stores only `Run` metadata, notes and scroll identifications. There's no `SaveFile`, so the header shows the run's name, class, race, last floor and last seen date. Character, Backpack and Kills show an empty state ("Stats are only available for the live run"). The notes and scroll tabs show that run's data, **read-only** (the current floor is the run's `last_floor`). Floors and Alchemy work as normal.

While in past-run mode, the save watcher keeps running. If a save loads for a different `gamekey` than the live run held before, the "New run detected" banner appears. Either way, the live data is updated in the background, so "Back to live run" is instant.

### Runs browser (dialog)

A table of `journal.runs()`: character, class, race, last floor, first seen, last seen. The live run is marked. It has Open (switches to past-run mode, or back to live if the live run is chosen) and Delete (asks for confirmation first, then `delete_run`). The live run can't be deleted.

### Save slot picker (dialog)

A table of `find_saves(dirs)`: slot number, singleplayer or multiplayer, modded, modified time, and the character name (from `load_save`; shows "unreadable" on `InvalidSaveError`). The first row is **"Most recent save (automatic)"**, which is the default. Choosing a row sets what the controller follows.

### Save following and watching

- **What's followed:** either "latest" (whatever `latest_save(dirs)` returns) or one specific save path.
- **Folder:** the remembered folder if there is one, otherwise `default_save_dirs()`. If no saves are found, the main area shows an empty state, "No Barony saves found", with a **Choose save folder…** button (most relevant on Windows). The choice is remembered.
- **Watching:** a `QFileSystemWatcher` on the followed file *and* its folder. Change events are debounced with a single-shot `QTimer` of about 300 ms. On change: re-resolve the followed save (in "latest" mode a different slot may now be newest), then `load_save` → `record_run` → update.
- **Errors:** on `InvalidSaveError`, keep the last good data, show the error banner, and retry up to 5 times about 1 s apart. The banner clears on the next good load. On `FileNotFoundError` (file replaced or deleted), re-add the watch and treat it the same way.
- If the file watch is dropped (the file was replaced), add it again after each change.
- **The followed save disappears for good** (Barony deletes a singleplayer save on death or victory, or the user deletes the slot): once the retries run out, the last run **stays on screen as an "ended" live run**, with a banner ("Save no longer found: this run may have ended"). Its notes and scroll IDs **stay editable**, because the journal is still valid and this is exactly when end-of-run notes get written. The "No Barony saves found" empty state is shown **only when there's nothing to display at all** (e.g. first launch).
- **"Latest" mode never switches back to an older save.** Re-resolving only adopts a save whose modified time is newer than the last one loaded. If that newer save belongs to a different `gamekey` (a new run started), live mode switches to it, since that's the run being played. The banner-instead-of-switching rule applies in past-run mode, as decided above.

### Secret levels (decided by the user: separate notes)

The save's top-level `level_track` field marks a secret level. It's **confirmed** from a real save: `dungeon_lvl: 3, level_track: 1` inside the Gnomish Mines, and `0` on main floors. A "floor" is therefore `(dungeon_lvl, secret)`, not just a depth. This needs small changes **outside the UI**, made first, with tests:

- **`data`:** parse `level_track` into `SaveFile` (e.g. `in_secret_level: bool`), and treat any value other than 0/1 as `InvalidSaveError`. Add the secret-level save as a test fixture (`tests/save_file_secret_level.baronsave`, copied from the user's `savegame1`, Gnomish Mines, depth 3).
- **`journal`:** add the flag to the floor-note key, `(gamekey, dungeon_lvl, secret)`, with a schema migration (bump `SCHEMA_VERSION`, add a step in `_migrate`; existing notes become `secret = 0`). `floor_note` / `set_floor_note` / `floor_notes` take the flag (a keyword defaulting to main floor), and `floor_notes` returns keys that include it. `Run.last_floor` gets the same treatment, so past runs show the right place. Update `docs/data-layer.md` to match.
- **UI:**
  - The header shows the secret level's name (`secret_level_at(dungeon_lvl).name`, e.g. "Gnomish Mines · depth 3") instead of the main floor's area.
  - The Notes panel's floor editor is keyed by `(dungeon_lvl, secret)`.
  - The Floors table gets a row for each secret level, placed after the main floor at the same depth and visually indented. Those rows can be selected, and their notes edited, like any other.
  - The highlight follows the actual location.
  - The Underworld's depth-7 and depth-20 second floors are secret levels reached by trapdoor, and they work the same way.

### Floor notes when the floor changes

When a save for a new floor arrives while the Notes panel's floor editor **has focus**, the editor keeps the old floor open (after flushing) and shows an inline prompt: "Now on floor 4: [Switch]". It switches when the user clicks, or when the editor loses focus. Without focus, it switches straight away. So the Notes panel tracks its own "showing floor" separately from the run's current floor.

### Notes autosave

Edits save after about 600 ms with no typing, through `set_run_note` / `set_floor_note`. Pending edits are flushed straight away before switching runs, when the floor changes, before a layout switch, and on window close. If the same floor note is open in the Notes panel and the Floors detail at once, the controller emits `floor_note_changed(gamekey, dungeon_lvl)`, and the other editor reloads it unless it has focus.

### Structure

```
src/barons_journal/ui/
  __init__.py         # run(): QApplication, settings, MainWindow, exec
  controller.py       # SessionController(QObject): Journal, watcher, follow mode, live/past state, signals
  settings.py         # thin typed wrapper over QSettings
  main_window.py      # QMainWindow: menus, header, layout switching
  layouts.py          # build/apply layout A and C from the panel instances
  panels/  header.py  character.py  notes.py  backpack.py  floors.py  alchemy.py  scrolls.py  kills.py
  dialogs/ runs_browser.py  slot_picker.py
```

`barons_journal.main()` calls `ui.run()`. The controller has signals along the lines of `live_save_loaded(SaveFile)`, `view_changed(ViewState)`, `save_error(str)`, `new_run_detected(int)` and `floor_note_changed(int, int)`. The panels get the controller (or only its signals) and render. They don't talk to each other directly. Tables use model/view (`QAbstractTableModel`) where the data is tabular: floors, kills, runs, slots, backpack.

### Settings (QSettings)

Layout choice, save folder, follow mode (latest or a path), window geometry and state, splitter sizes per layout, and panel visibility. First launch opens maximised in layout C.

### Testing

Add `pytest-qt` as a dev dependency. Tests use `tests/save_file_example.baronsave` copied into `tmp_path`, plus a journal in `tmp_path`, never the real one. Cover:
- the controller: load → `record_run`, error retry with last-good kept, the latest-vs-pinned slot, new-run detection in past mode, and note flush on switch
- each panel rendering the sample save
- unidentified items never showing their true names (a test with an unidentified item)
- layout switching keeping the same panel instances and text being typed
- the scroll tab's identify/undo/error paths
- the empty states (no saves, past run)

## Calls made by Claude (please check)

- **Look:** Qt's Fusion style, following the system's light/dark scheme. No custom theme beyond small touches like the HP/MP bar colours and the highlighted current floor.
- **Past runs are read-only:** notes and scroll IDs can be viewed but not edited there.
- **Autosaving notes** with no Save button, and the debounce and retry timings above.
- **Remembering** the layout, folder, followed slot, geometry and panel sizes.
- **Panel contents and placement** as described, including Backpack and Kills under Character in layout A, and spells as a list in the Backpack panel.
- **Floor notes editable from the Floors tab** as well as the Notes panel, for any floor.
- **No worker threads.**
- **A run whose save disappears stays on screen**, still editable, with an "ended" banner. "Latest" mode never adopts an older save.
- **The floor-note editor doesn't jump floors while focused.** It offers a "Switch" prompt instead.
