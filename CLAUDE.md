# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Baron's Journal is a native desktop companion app for the game Barony (Python 3.13+, managed with uv). Features: read-only stats for the current run, pulled from the save file; scratchpad notes per run and per floor; floor reference info (secret levels, artifacts); and potion recipes.

**Status:** the non-UI layers are done and tested: save discovery and parsing (`data`), ID-to-name tables (`data.ids`), reference data for scrolls, alchemy, and floors (`reference`), and the user's SQLite journal (`journal`). The PySide6 UI is built (`ui`); `main()` in `src/barons_journal/__init__.py` calls `ui.run()`. Design notes are in `plans/` (gitignored, local only).

## Commands

```
uv sync                      # install dependencies (includes PySide6)
uv run barons-journal        # run the app ([project.scripts] entry -> barons_journal:main)
uv run pytest                # run the tests (pytest is a dev dependency)
uv run pytest tests/data/test_saves.py::TestFindSaves   # run one file or test
```

## UI (`src/barons_journal/ui/`)

**Read `docs/data-layer.md` first.** It covers the public API of the data, reference, and journal packages, and the rules the UI must follow (spoilers, `record_run`, threading). Toolkit: PySide6 (Qt 6). Only `ui` may import Qt; `data`, `reference`, and `journal` must not.

- `__init__.py`: `run()` builds the `QApplication`, `AppSettings`, `Journal`, `SessionController` and `MainWindow`.
- `controller.py`: `SessionController` owns the session. It finds saves, watches the followed save and its folder (`QFileSystemWatcher`, debounced), and on change runs `load_save` → `journal.record_run(save)` → emits `view_changed(ViewState)`. A save read mid-write (`InvalidSaveError`) keeps the last good data and retries on a `QTimer`. It also handles past runs (read-only), notes, and scroll identification. Every `Journal` call stays on the main thread.
- `state.py`: `ViewState`, the immutable snapshot panels render. `location.py`: `Location(dungeon_lvl, secret)` and its wording. `settings.py`: `AppSettings` (QSettings: layout, save folder, followed save, geometry, splitter sizes, panel visibility).
- `theme.py`: `apply_theme(app, "barony" | "system")` sets the app palette and stylesheet (dark stone/wood, parchment text, gold accents, red/blue HP/MP bars). It's called from `run()` and from View → Theme, and saved in `AppSettings.theme`. Panels hook into the stylesheet through object names (`hpBar`, `mpBar`, `runTitle`) and a `role` property (`section`, `muted`) rather than setting colours themselves.
- `layouts.py`: `Panels` and `LayoutManager` build the Focus layout (character | tabs: Backpack, Floors, Alchemy, Scrolls, Kills | notes) and the Dashboard layout from the same panel instances. `main_window.py`: menus (File, Runs, View), run header, empty state, close handling (flushes notes).
- `panels/`: `header`, `character`, `notes` (run note and current-floor note), `backpack`, `kills`, `floors` (table plus per-floor note, secret levels included), `alchemy`, `scrolls`; `_stats.py` holds shared bases for the table panels.
- `popouts/`: always-on-top widget windows toggled from View → Widgets (`views.py`: Vitals, Attributes, Skills, Floor note, Current floor; `map.py`: Map, a frameless translucent frame laid over the game's map with marker icons from `icons/`, kept in memory only and cleared when the floor changes; `manager.py`: `PopoutWindow`, `PopoutManager`, open state and geometry in `AppSettings`). Windows are parentless `Qt.Dialog | WindowStaysOnTopHint` because COSMIC tiles `Tool` windows. `run()` calls `prefer_xwayland()` (`QT_QPA_PLATFORM=xcb;wayland`, falling back to native Wayland) since native Wayland lets no app stay on top; on COSMIC, app-requested positions are ignored, so only size is restored.
- `widgets/note_editor.py`: `NoteEditor`, a plain-text editor that saves on a timer, on focus out, and on `flush()`. `dialogs/`: `runs_browser` (past runs) and `slot_picker` (which save slot to follow).
- Tests are in `tests/ui/` and run on the offscreen Qt platform.
- On Windows the saves live in the game's install folder, so the UI lets the user pick the folder when none is found.

## Architecture

- **Package layout:** src-layout, built with the `uv_build` backend. Code lives in `src/barons_journal/`.
- **Save parsing (`barons_journal.data`):** Barony's save files are **JSON**. The game writes them as `savegame<N>.baronysave` (N = slot 0-99; multiplayer adds `_mp` and mods add `_modded` before the extension) in `~/.barony/savegames/` on Linux and macOS, or `<install folder>/savegames` on Windows. `data/saves.py` handles this; the sample in `tests/` is named `.baronsave`. Validate with `magic_cookie == "BARONYJSONSAVE"` and check `game_version`. `tests/save_file_example.baronsave` is a real save to develop and test against. The plan is to keep all raw-dict handling and quirk cleanup inside `data` and give the UI typed models only (`SaveFile`, `Player`, `Stats`, ...).
- **Where the data is:** the local player is `players[player_num]`. Most stats are under `players[n].stats` (`HP`/`maxHP`, `MP`/`maxMP`, `STR`/`DEX`/`CON`/`INT`/`PER`/`CHR`, `LVL`, `GOLD`, `PROFICIENCIES`). `stats.player_equipment` maps slot names to **indices into `stats.inventory`** (local player only; other players use `npc_equipment`). Learned spells are inventory items of type `SPELL_ITEM` (162) whose `appearance` is the spell ID. `EFFECTS`/`EFFECTS_TIMERS` have 160 slots (only 0-134 are defined); timers are in ticks, 50 per second. `gamekey` stays the same for the whole run, so it's the key for run notes; floor notes use `(gamekey, dungeon_lvl, secret)`.
- **Save quirks to handle:**
  - The player object has a duplicate `"race"` key. Python's `json` keeps the last one.
  - Names end in `\r` (`game_name`, `stats.name`). Strip them.
  - `4294967295` (uint32 -1) means empty or none.
  - Class, race, kills, proficiencies, items, and spells are numeric IDs (list positions in Barony's C++ enums). `barons_journal.data.ids` maps them to in-game names from `ids.json`. Don't hand-edit that file: regenerate it with `scripts/build_id_tables.py <Barony checkout> --game-dir <installed Barony>`, which reads the enums and `lang/` files from `TurningWheel/Barony`. Status effect names aren't in the source repo, so they come from `data/status_effects.json` in the installed game (Steam: `~/.steam/steam/steamapps/common/Barony`). The Barony Save Editor (Groshie) is a useful cross-reference, but its spell list is missing `SPELL_DUCK_DIVE` (218), so spells from 218 on are shifted by one.
- **Save timing:** Barony writes the save on floor transitions, not continuously, so the stats view is always a snapshot.
- **Scrolls (`barons_journal.reference`):** `SCROLLS` (16 types) and `SCROLL_LABELS` (the 25 unidentified labels, in game order) come from `scrolls.json`; regenerate with `scripts/build_scroll_tables.py`, which takes the same arguments as the ID script. Each run shuffles a fixed 25-entry scroll list (`enchantedFeatherScrollsFixedList` in `items.hpp`, seeded from `gamekey`) and label `i` goes to entry `i`. Some scrolls take several labels (`label_count`: Fire and Destroy Armor have 3), so identifying one label doesn't rule that scroll out for the other labels. The plan is for the UI to record label -> scroll as the player identifies them. Don't compute the mapping from the seed. The save's player-level `scrolls` field (`known_scrolls` in `scores.cpp`) is a list of ints, probably label indices the player has learned; this isn't confirmed yet.
- **Alchemy and floors (`barons_journal.reference`):** `RECIPES`/`mix()` come from `alchemy.json` (rebuild with `scripts/build_alchemy_table.py <Barony checkout>`, which parses `alchemyMixResult` in `interface.cpp`; the water/polymorph/acid rules are written in code in `alchemy.py`). `FLOORS`/`SECRET_LEVELS` come from `floors.json` (rebuild with `scripts/build_floor_table.py <checkout> --game-dir <install>`). A secret entrance on main floor N leads to secret level N+1. Which floors have one comes from the `// secret stuff` block in `maps.cpp`, plus floor 5, whose entrance is part of a fixed map. Mystic orb floors come from `orb_floors` in `maps.cpp`. Whether a secret level's exit continues to the next secret level is stored in binary map files and isn't modelled.
- **Unidentified items keep their true type in the save.** An unidentified scroll of fire is saved as type 75 with `identified: false`. The UI must show `Item.name` (which respects `identified`) and never the raw `type`/`item_id` of an unidentified item, or it gives away what the item is. For the same reason the app doesn't show an unidentified scroll's label: the label depends on the per-run shuffle, and working it out would mean computing the mapping.
- **Journal (`barons_journal.journal`):** the user's own data, in SQLite at `default_journal_path()` (XDG data dir / `%APPDATA%` / `~/Library/Application Support`). `Journal` stores runs keyed by `gamekey` (character, class, race, last floor and whether it was a secret level (`last_floor_secret`), first/last seen, taken from the save's timestamp), plus scroll identifications keyed by `(gamekey, label)`, run notes keyed by `gamekey`, and floor notes keyed by `(gamekey, dungeon_lvl, secret)`. Everything references `runs` through a foreign key with cascading delete, so call `record_run(save)` whenever a save is loaded, before writing anything for that run. An empty note deletes the row. `ScrollProgress` is plain logic with no SQLite: it uses `label_count` to work out which scrolls each unknown label can still be, and rejects impossible states (e.g. a 4th Fire label). The schema version is in `PRAGMA user_version`; bump `SCHEMA_VERSION` and add a migration step in `Journal._migrate` when the schema changes.
- **Data kept apart:** user notes go in the app's own storage, never in game files. Static reference data (floors, potion recipes) ships as curated JSON, separate from the save parser.
